Firefly is the encrypted messaging engine underneath Lupyd, released as open source. It implements Messaging Layer Security (MLS, RFC 9420), the IETF standard for end-to-end encrypted groups, and wraps it in a client that handles everything an app needs around the cryptography: connecting, persisting state, syncing devices and recovering from bad networks.

the middle column up there is all the server ever gets

Why MLS

Pairwise protocols encrypt each message once per recipient, so a group of a thousand devices costs a thousand encryptions per message. MLS arranges the group’s keys in a ratchet tree, so adding, removing or rotating a member costs a logarithmic number of operations. It also gives forward secrecy and post-compromise security: a leaked key stops being useful once the group moves on.

In Firefly every device is a member of the group in its own right, so a conversation follows a person across their phone and laptop without the server ever holding a readable message.

The unit tests cover the cryptographic rules, the SQLite stores and key storage, and run entirely in memory. The integration suite runs against a real server and PostgreSQL, and skips itself when no server is configured so offline CI stays fast.

WebSocket to WebTransport, without breaking anyone

Firefly started on WebSockets. I added WebTransport (HTTP/3 over QUIC) beside it with the same API: the client picks the transport from the URL, so existing apps switch by changing one string.

Under the hood the two work differently. On a WebSocket every request shares one TCP stream, so one lost packet stalls everything behind it. On WebTransport each request gets its own bidirectional QUIC stream, and server pushes arrive on a separate unidirectional one, so a loss only delays the stream it hit. QUIC also survives a switch from Wi-Fi to cellular without a new handshake.

To check it was worth it, I benchmarked both on 500 members with 3 devices each (1,500 live endpoints) for five minutes each, with deterministic traffic and a client network shaped by tc netem to 30 ms latency, ±5 ms jitter and 1% packet loss, like a phone on a busy cell.

MetricWebSocketWebTransport
Median RPC latency33.2 ms33.5 ms
p99 RPC latency258.7 ms51.2 ms
Worst RPC latency536.0 ms227.1 ms
Latency std dev24.4 ms10.1 ms

Peak client memory209 MB282 MB
Bandwidth98.6 KB/s145.9 KB/s

The medians are identical because both sit on the network floor. The tail is where TCP’s head-of-line blocking shows: WebSocket’s p99 is five times worse. QUIC pays for that with about a third more client memory and half again the bandwidth, a trade worth making for a chat app.
